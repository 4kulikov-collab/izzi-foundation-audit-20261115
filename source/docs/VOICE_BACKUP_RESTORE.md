# Локальное восстановление обращения, выпусков и WAV

На базе 41eee5c добавлен отдельный операторский модуль `worksheet_reviews.voice_backup`. Старые `backup_local` / `restore_local` по-прежнему работают только с SQLite и **не восстанавливают внешнее аудио**. Новый сценарий проверен только на полностью синтетическом стенде без сервера и сети.

Izzi сохраняет три цели: помощник менеджера по обращениям CRM и презентациям; связь каждого выпуска, повторной подборки и файлов с обращением для контроля директора; будущий самостоятельный бот с памятью и навыками менеджера. Менять цели может только Никита. Это продукт туристической компании, не Академия или тренажёр.

## Что сохраняется

Один ZIP без сжатия: `database.sqlite3`, `manifest.json`, `audio/0000.wav` и следующие WAV. Снимок SQLite включает обращения, версии, подтверждения, связи, HTML/PDF, все голосовые записи и состояния отзыва на момент копирования. Manifest сопоставляет каждый WAV с точным приватным путём в БД, SHA-256, размером и длительностью. Исходники не редактируются. Внешние WAV не заменяются тишиной при пропаже: весь backup/restore завершается отказом.

Снимок создаётся штатным SQLite backup. В копии удаляются сеансы входа, затем выполняется VACUUM; исходная БД не изменяется. Ключ приложения, переменные окружения и произвольные соседние файлы не включаются. Восстановленная копия теперь имеет внутренний SQLite-маркер блокировки; настройки приложения отказывают до создания нового ключа. Простой вход со старым паролем не считается повторной авторизацией. См. [актуальный контракт](RESTORE_AUTHORIZATION.md). Парольные хеши и внутренние тексты в БД остаются.

**Это внутренняя незашифрованная копия, не клиентский файл. Не отправлять туристам, не добавлять в Git/PR или демонстрационные файлы.** SHA-256 обнаруживает повреждение, но не доказывает подлинность архива от недоверенного отправителя: тот может заменить и данные, и manifest. Шифрование, подпись, независимое хранение ключей, журнал удалений, RPO/RTO и аварийная эксплуатационная приёмка не реализованы этим этапом.

## Доступ и публикация восстановления

Python API требует `synthetic_only=True` и активного локального superuser-оператора. Проверяется актуальная запись пользователя до работы и перед публикацией результата; обычный менеджер не получает копию всей БД. Это не новая директорская роль или HTTP-метод. Пользователь и права создаются только внутри одноразового теста; существующие аккаунты не меняются. Владелец ОС с доступом к БД/файлам остаётся за пределами этой прикладной проверки.

```python
from worksheet_reviews.voice_backup import (
    create_voice_bundle, restore_voice_bundle, verify_restored_copy,
)
# Только disposable synthetic settings/DB и тестовый оператор:
create_voice_bundle(new_zip_path, actor=synthetic_operator, synthetic_only=True)
root = restore_voice_bundle(new_zip_path, new_entry_json_path,
                            actor=synthetic_operator, synthetic_only=True)
assert verify_restored_copy(new_entry_json_path) == root
```

Пути должны быть вне репозитория, родительский каталог уже должен существовать. Существующие назначения и симлинки отклоняются. Restore не перезаписывает активную БД и не меняет конфигурацию. Он готовит новый приватный каталог рядом с `new_entry_json_path`: `prototype.sqlite3`, `private-audio/...`, manifest и квитанция. После полной проверки единственная операция `os.link` публикует **новый файл-указатель JSON**, не заменяя существующий. Приложение само этот указатель не читает.

До публикации все сбои удаляют подготовленный каталог; пригодная для подключения частичная копия не выдаётся. Конкурентно появившийся файл назначения остаётся цел. Если файловая система не поддерживает hard link, операция завершается отказом; небезопасной запасной перезаписи нет. Передача `root` через `TRAVELHUB_DATA_DIR` теперь приводит к явному отказу запуска Django. `verify_restored_copy` проверяет целостность **заблокированной** копии, а не разрешение её использовать. Квитанция restore-v2 содержит отдельный SHA изменённой копии SQLite; исходный manifest backup сохраняется неизменным. Старые квитанции v1 не признаются безопасным результатом восстановления; исходные backup-v1 принимаются новым restore и блокируются.

Проверяются состав ZIP, повторы/лишние элементы, отсутствие сжатия/симлинков, ограниченные размеры, совместимость миграций/схем, целостность SQLite, FK, хеши версий/PDF и связи голосового источника/владельца/подборки. WAV сверяется с БД, SHA и настоящим PCM-заголовком. Временные пределы: SQLite 64 МиБ, до 32 WAV, каждый до 5 МиБ/300 секунд, manifest 64 КиБ. Это границы локального протокола, не согласованные production-квоты.

Атомарность проверена при внедрённых программных сбоях и конфликте назначения. Внезапное отключение питания, ошибки диска при уборке, действия привилегированного ОС-пользователя, реальная конкурентная запись/удаление исходников и перенос на другую ОС не проверены. Рабочий стенд должен быть остановлен перед будущим переносом; здесь все исходные данные принадлежат одному синтетическому процессу. Удаления/отзывы **после** снимка автоматически не переносятся назад в старый backup — для production нужен отдельный журнал и проверенный порядок восстановления.

## Воспроизведение без сети

Из корня уже подготовленного репозитория с установленными зависимостями:

```bash
.venv/bin/python manage.py test worksheet_reviews.test_voice_backup --verbosity 1
.venv/bin/python scripts/voice_backup_restore_smoke.py
```

Для полного прогона в изолированной временной папке Linux/Mac-shell:

```bash
TRAVELHUB_DATA_DIR=$(mktemp -d) TESSDATA_PREFIX="$PWD/.local-state/tessdata" \
  .venv/bin/python manage.py test --verbosity 1
```

На Windows используются существующий Python/venv и отдельный временный `TRAVELHUB_DATA_DIR`; написание `.\.venv\Scripts\python.exe` вместо `.venv/bin/python` — только инструкция, **не результат проверки Windows**. Новые зависимости скачивать для этого этапа не требуется. Не запускать команды против реальной БД.

Smoke переиспользует прежний `voice_ledger_smoke`, а не переписывает бизнес-сценарий. Он создаёт синтетические Inquiry + два PDF + silent WAV, сохраняет внутренний архив и контрольные значения, завершает исходный процесс и **удаляет исходный каталог БД/аудио**. Второй процесс восстанавливает пакет. Третий процесс проверяет отказ старта Django, затем читает SQLite/WAV напрямую для сверки исходных байтов, хешей, связей, подтверждений и сохранённого отзыва выпуска. Третья подборка больше не создаётся: восстановленная копия не получила повторную авторизацию. Старый результат с третьим выпуском относится к прежней версии и не является текущим поведением. В клиентском HTML/JSON и извлечённом PDF-тексте нет внутренней контрольной строки, расшифровки и пути WAV. В конце все БД, ключи, WAV и внутренний backup удаляются; наружу выводится только обезличенный JSON проверки. Сетевые DNS/connect/bind запрещены внутри каждого процесса, сервер не запускается.

36 новых тестов покрывают круговое восстановление, отказ при отсутствии/повреждении WAV/БД/ZIP/схемы/связи, ложный путь, лишний/повторный/сжатый ZIP-элемент, лимит размера, недоступность оператора, отзыв доступа до публикации, частичную запись, отказ проверки/публикации, конфликт назначения, отсутствие сеансов и ключа, повреждение после восстановления.

## Границы результата

SpeechKit/Luna остаются выключены. Silent WAV и заданные текст/поля — заглушки, не распознавание или синтез речи. U-ON не синхронизировано; OCR, перелёты, Telegram/MAX voice и реальное расширение не подключались. Межменеджерская роль директора не добавлена. Native Mac, Windows Chrome/Яндекс, browser file://, реальное аудио, production и полное R30/T45 с ключами/RPO/RTO не проверены. Запрет file:// не повторялся и не обходился. Проверены только локальные части R19/R22/R25/R26/R30, T25/T26/T34/T42/T45/T46. Результаты — [отчёт](../qa-voice-backup-20261115/REPORT.md).
